SECTION 2 — EMISSIONS FACTOR STORAGE
================================================================================

Primary factor table: background_grade_metrics

- Each row has a UUID id (the factor identifier).
  This is the metric_id referenced by activity_data.

- Factors are NOT stored as simple key-value pairs.
  Each row carries multiple classification attributes:
    factor_set_id, grade_id, jurisdiction_id, mastertype_id, typecast_id,
    emissions_category_id, emissions_subcategory_id, emissions_source,
    lifecycle_module_code, ghg_scope_id, metric_type_id, band_code, unit_id.

- The numeric factor value is in the `value` column (Numeric, nullable).

- background_grade_metrics rows belong to an emissions_factor_sets record,
  which in turn belongs to a dataset_revisions record.

- Reference by ID:
  activity_data.metric_id is a direct UUID FK to background_grade_metrics.id.
  No dynamic resolution by attributes at the ORM layer during calculation;
  the calculator fetches the metric by its ID directly.

- Versioning:
  Multiple versions coexist. Old metric rows are NOT overwritten.
  A new EmissionsFactorSet is created under a new DatasetRevision.
  The is_active boolean on background_grade_metrics marks current rows.

- Legacy factor tables:
  emission_factor, emission_factor_value, emission_source exist in lookup_data.py
  and are referenced by the legacy emission_entry model.
  These are SEPARATE from the active background_grade_metrics system.

- Other factor-type tables (electric_decarb_factors, ev_uptake_factors,
  freight_rail_factors, vepm_factors, maintenance_replacement_factors, fugitives)
  each carry their own dataset_revision_id FK and are NOT linked through
  emissions_factor_sets.

SECTION 3 — VERSIONING / TIME HANDLING
================================================================================

dataset_revisions:
  - status         : String(20), values: draft | published | deprecated | archived
                     Server default: "draft"
  - applicable_from: Date, nullable
  - applicable_to  : Date, nullable
  - scope_type     : String(20), values: DEFAULT | ORG | PROJECT
                     Server default: "DEFAULT"
  - created_at     : TIMESTAMP

emissions_factor_sets:
  - version    : String, nullable (free-text label)
  - valid_from : Date, nullable
  - valid_to   : Date, nullable
  - is_locked  : Boolean, server default false

background_grade_metrics:
  - is_active  : Boolean, server default true
  - created_at : TIMESTAMP
  NOTE: No effective_from / effective_to date fields on this table.

default_transport_distances / default_waste_rates / material_recycled_content:
  - effective_from : Date, nullable
  - effective_to   : Date, nullable
  - is_active      : Boolean

proponent_assumption_overrides:
  - effective_from : Date, NOT NULL
  - effective_to   : Date, nullable

project_stage_instances:
  - approval_status      : String(20)
    Values: draft | submitted | in_review | tech_approved | final_approved
  - approved_at          : TIMESTAMP, nullable
  - technical_approved_at: TIMESTAMP, nullable
  - submitted_at         : TIMESTAMP, nullable

Effect of factor changes on historical calculations:
  - emissions_results stores the computed value (tCO2e) as a plain Numeric.
  - It does NOT store: the factor value used, the metric_id, or the
    dataset_revision_id at the time of calculation.
  - There is NO FK from emissions_results to background_grade_metrics
    or dataset_revisions.
  - If a metric row value is edited in-place, previous emissions_results rows
    are unaffected (they store the result, not the factor).
  - If a metric row is deactivated and a new one created (different UUID),
    activity_data.metric_id still points to the old row unless explicitly re-linked.

  unit_id                     | UUID FK, nullable   | → units.id (RESTRICT)

  lifecycle_module_code       | String FK, nullable | → lifecycle_modules.code

- Activity links to a project DIRECTLY via project_id.
- Activity links to a stage via project_stage_instance_id.
- Activity references an emissions factor DIRECTLY BY ID
  (metric_id → background_grade_metrics.id).
- Lifecycle stage IS stored on the activity row:
    - project_stage_instance_id binds it to a stage instance
    - lifecycle_module_code stores a module code (e.g. "A1-A3", "B2-5")
      which may be overridden at the row level.
- For "refurbishment" rows (ui_table_key == "refurbishment"):
    - metric_id may be NULL
    - extra_fields["mr_factor_id"] holds a UUID pointing to
      maintenance_replacement_factors.id

Legacy activity table: emission_entry
  - Links directly to emission_factor.id
  - Links to project_reporting_submission.id
  - Stores pre-calculated emissions_tco2e
  - SEPARATE from the current activity_data system

SECTION 5 — RESULTS STORAGE
================================================================================

Results ARE STORED in the emissions_results table.
They are NOT calculated on the fly at query time.

Table: emissions_results

  Column                    | Links to / Type
  --------------------------|------------------------------------------------
  id                        | UUID PK
  activity_data_id          | UUID FK → activity_data.id (CASCADE)
  project_id                | UUID FK → project.id (CASCADE)
  project_stage_instance_id | UUID FK → project_stage_instances.id (CASCADE)
  lifecycle_module_code     | String FK → lifecycle_modules.code (nullable)
  value                     | Numeric — the computed tCO2e
  unit_id                   | UUID, nullable — NO FK constraint in ORM model
  created_at                | TIMESTAMP

- UniqueConstraint("activity_data_id", "lifecycle_module_code"):
  One result row per activity + module combination.
  The calculator uses an UPSERT pattern (overwrites on recalculation).

- No FK from emissions_results to background_grade_metrics,
  emissions_factor_sets, or dataset_revisions.
  The factor value used at calculation time is NOT recorded.

- No stage or phase field beyond project_stage_instance_id and
  lifecycle_module_code.

SECTION 7 — PERMISSIONS & EDITING
================================================================================

Database layer:
  NO row-level security, CHECK constraints, or view grants enforce permissions
  on datasets or activities at the database layer.

Application layer:
  All permission enforcement is application-layer only.

  core/rbac.py:
    - Defines role name string constants (see below)
    - get_effective_role_names() queries user_roles JOIN roles at runtime,
      unioning across GLOBAL, ORGANISATION, PROJECT, and STAGE scopes

  core/access_context.py:
    - get_dataset_visibility_context() returns DatasetVisibility enum (DEFAULT|ORG|PROJECT)
    - NOTE: The file's own docstring states "NO dataset queries are performed here yet"
      — the function is implemented but not yet applied to dataset filtering

Role names (hardcoded string constants in core/rbac.py):
  SUPER_ADMIN    = "SUPER_ADMIN"
  ORG_ADMIN      = "ORG_ADMIN"
  PROJECT_ADMIN  = "PROJECT_ADMIN"
  PROJECT_EDITOR = "PROJECT_EDITOR"
  PROJECT_VIEWER = "PROJECT_VIEWER"
  GENERAL_USER   = "GENERAL_USER"

Role grant ceiling (hardcoded dict in core/rbac.py):
  SUPER_ADMIN   can grant: SUPER_ADMIN, ORG_ADMIN
  ORG_ADMIN     can grant: PROJECT_ADMIN
  PROJECT_ADMIN can grant: PROJECT_EDITOR, PROJECT_VIEWER

Role scoping (user_roles table):
  scope_type: GLOBAL | ORGANISATION | PROJECT | STAGE
  scope_id  : UUID (holds org_id or project_id depending on scope_type)

Tables involved:
  roles, permissions, role_permissions, user_roles, access_requests

SECTION 8 — EXISTING CALCULATION LOGIC
================================================================================

All calculation logic is in Python service files under backend/services/.
No stored procedures or PostgreSQL functions exist for calculations.

Two PostgreSQL views are queried via raw SQL text():
  v_grade1_asset_level_pivoted  — definition in sql/create_view_grade1_pivoted.sql
  v_grade2_component_level      — definition file NOT PRESENT in tracked sql/ directory

Service files and their factor sources:

  emissions_calculator.py
    Type   : Per-activity_data row
    Formula: tCO2e = quantity × metric.value
    Factors: background_grade_metrics.value (fetched by metric_id)
             Fallback for ui_table_key == "refurbishment":
               maintenance_replacement_factors.emissions_intensity_tco2e
               (fetched by extra_fields["mr_factor_id"])
    Trigger: Called synchronously after every activity_data POST / PATCH

  grade1_asset_calculations.py
    Type   : Grade 1 asset-level
    Formula: Emissions = material_share × quantity × emission_intensity
             for stages A1-A3, A4, A5
    Factors: PostgreSQL view v_grade1_asset_level_pivoted (raw SQL)

  grade2_component_calculations.py
    Type   : Grade 2 component-level
    Formula: Emissions = factor × quantity for A1-3, A4, A5
    Factors: PostgreSQL view v_grade2_component_level (raw SQL)

  grade2_b4_replacement_calculations.py         — UNCLEAR FROM CODE (not fully read)
